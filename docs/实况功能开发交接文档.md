## 三、实况需求的原始问题

### 3.1 原问题

项目原本已经能识别和下载抖音 `实况` 作品，但下载结果是视频格式文件。

用户希望先通过真实样本验证问题，再决定功能目标。

测试样本使用的是这条抖音分享文本：

```text
4.69 复制打开抖音，看看【全网无前任，的图文作品】有我就够了吗。# 素颜原相机  https://v.douyin.com/3YOfA2C8D0g/ G@i.Ch 07/13 SYM:/
```

### 3.2 真实测试结论

基于项目实际运行，确认该作品被识别为：

- 作品 ID：`7617127364405264613`
- 类型：`实况`

在原始实现里：

- `Extractor` 将实况内容提取成视频下载地址
- `Downloader` 将其按 `mp4` 形式落地

所以最终结果是“单个 mp4 文件”，而不是“更接近 live/photo 的结构”。

## 四、这次实况改造做了什么

### 4.1 核心目标变化

本次实现没有试图生成 Apple 原生单文件 `Live Photo`。

真正完成的目标是：

- 将抖音 `实况` 从“只下载成视频”
- 改为“下载成配对资源”

当前支持两种导出形式：

- 默认：`jpeg + mp4`
- 可选：`jpeg + mov`

### 4.2 对上游数据的理解变化

本次工作确认了一个重要认知：

`抖音接口对实况作品的表达，不是一个单独 live 文件，而是拆分后的图片资源 + 动态视频资源。`

也就是说，系统拿到的第一手数据不是：

- 一个完整的 live 单文件

而是：

- 一张静态图
- 一段动态视频

因此项目最合理的下载落地形式，本来就应当是配对导出，而不是假设存在一个直接可取的完整 live 文件。

## 五、实况解析链路的工程理解

当前抖音 `实况` 作品的处理链路可以概括为：

1. 作品详情接口返回一个 `aweme detail` JSON
2. `Extractor` 在 `images` 结构里发现某个条目同时带有图片信息和视频信息
3. 系统将该作品类型判断为 `实况`
4. 提取器将每个条目整理为：

```python
{
    "image": "静态图地址",
    "video": "动态视频地址",
}
```

5. `downloads` 变成对象数组，而不是纯 URL 字符串数组
6. 下载器按导出模式分别下载静态图和动态视频

一句话总结：

`当前系统对实况的理解是：它不是普通视频，也不是普通图集，而是“带有静态图 + 动态视频”的特殊图集。`

## 七、关键设计决策与经验结论

### 7.1 为什么默认选择 `jpeg + mp4`

一度做过 `jpeg + mov` 的 Apple 风格导出探索，但后来明确收束为：

- 默认导出：`jpeg + mp4`
- 可选模式：`jpeg + mov`

原因：

- 如果不继续追 Apple 生态兼容，单纯把 `mp4` remux 为 `mov` 意义不大
- `mov` 不等于 Apple 原生 Live Photo
- 即使只是 remux，不重编码，也会额外消耗一次磁盘读写和封装步骤
- `mp4` 的兼容性反而更普遍

所以最终决策是：

`默认实用主义，保留 Apple 风格作为可选项，但不把它设为默认。`

### 7.2 为什么没有继续做“单文件原生 Live Photo”

本轮已经明确得出的工程判断是：

- iPhone 原生 `Live Photo` 不是通用单文件格式
- 它本质上是 `照片资源 + 配对视频资源`
- Apple 生态识别依赖配对元数据，而不是仅靠后缀名

因此：

- 从 Linux 环境继续追“单文件原生 Live Photo”不值得
- 当前项目应把目标收敛为“配对资源导出”

### 7.3 抖音实况的正确工程认知

本轮最重要的认知资产是：

`抖音实况不是 Apple Live Photo 资产模型，而是抖音平台自己的内容模型。`

从平台角度看：

- Apple 的 Live Photo 是设备/相册资产语义
- 抖音的实况是跨平台内容分发语义

所以抖音接口自然更倾向于返回：

- 独立静态图
- 独立动态视频

而不是 Apple 风格的成对资产格式。

最终结论是：

- 值得作为研究计划存在

- 当前接口已经给出 `image + video`

- 继续逆向的投入和收益可能不成正比
