# 抖音实况上游接口探索计划

## 背景

当前项目已经支持解析抖音 `实况` 作品，并将其导出为两类资源：

- 默认模式：`jpeg + mp4`
- 可选 `apple` 模式：`jpeg + mov`

根据现有接口返回结果，项目拿到的上游数据是结构化的 `图片资源 + 动态视频资源`，而不是一个已经封装完成的单体 `Live Photo` 文件。

这说明当前实现并不是“少拿到了一个文件”，而是“上游接口本身就是以拆分资源的方式表达实况内容”。

## 目标

本计划的目标不是立即修改下载逻辑，而是验证一个更基础的问题：

`抖音作品详情或其关联接口中，是否存在比当前 image + video 更原始、更完整的实况资源表达？`

如果存在，后续再评估是否值得接入项目。

如果不存在，则维持当前 `jpeg + mp4` 为主、`jpeg + mov` 为辅的导出策略。

## 不在本计划范围内

以下内容不属于当前计划范围：

- 不以“生成 iPhone 原生单文件 Live Photo”为目标
- 不依赖 macOS 环境或 Apple 私有框架
- 不为了研究目的大范围重构现有下载链路
- 不提前假设抖音一定保存了 Apple 风格的配对资产

## 当前已知事实

基于当前项目实现与已完成测试，可以确认：

1. 抖音 `实况` 作品出现在作品详情数据的 `images` 结构中
2. `images` 条目不仅有静态图信息，还带有动态视频信息
3. 项目现在提取出的 `downloads` 结构为：

```python
[
    {
        "image": "静态图地址",
        "video": "动态视频地址",
    }
]
```

4. 当前没有发现“单一 live 文件下载地址”
5. 当前没有发现 Apple `Live Photo` 那类公开可用的成对资产元数据

## 核心假设

本计划围绕以下两个假设展开：

### 假设 A

当前公开作品详情接口已经是抖音对外分发的最终表达形式，`image + video` 就是最上游、最稳定、最通用的实况资源结构。

### 假设 B

抖音内部可能还存在更原始的实况资源表达，但没有暴露在当前项目使用的接口中；如果存在，也更可能出现在其他端、其他接口、上传链路或受限字段中。

## 为什么值得做一次有限探索

虽然当前功能已经可用，但仍有必要做一次小范围验证，原因如下：

1. 可以确认当前 `jpeg + mp4` 是否已经是最合理的最终方案
2. 可以避免未来重复讨论“是不是还藏着一个真正的 live 文件”
3. 如果确实存在更原始字段，后续可评估是否值得接入
4. 即使最终没有新发现，也能把结论沉淀成项目认知

## 探索策略

本计划只做“字段级”和“接口级”验证，不直接进入大规模逆向或实现阶段。

### 第一阶段：同作品多入口对比

针对同一条抖音 `实况` 作品，比较以下入口返回的差异：

- 当前项目使用的作品详情接口
- Web 端落地页相关接口
- App 端可能使用的详情接口
- 分享链路涉及的中间接口

重点不是抓全量请求，而是确认：

- `images` 的字段是否一致
- 是否存在额外 `origin`、`raw`、`live`、`motion` 一类字段
- 是否存在明显比当前 `image + video` 更接近原始素材的表达

### 第二阶段：字段语义排查

重点检查以下类型的字段：

- `live_photo`
- `motion_photo`
- `heic`
- `origin`
- `raw`
- `resource_type`
- `asset_id`
- `content_id`
- `paired_video`
- `dynamic_cover`
- `static_cover`

目标是判断：

- 是否存在配对资源标识
- 是否存在未转码资源
- 是否存在 Apple 风格的元数据痕迹

### 第三阶段：上传前后语义判断

如果能够拿到更多样本，重点比较：

- iPhone 端发布的实况
- 安卓端发布的实况
- 平台二次编辑后的实况

目的是判断：

- 主图是否来自上传端原始素材
- 主图是否被平台重新选帧
- 动态部分是否统一被平台转码

## 预期输出

本计划理想情况下只产出以下三类结果之一：

### 结果 1

没有发现比 `image + video` 更原始的公开资源表达。

结论：

- 当前实现已经贴近上游真实语义
- 默认保持 `jpeg + mp4`
- `apple` 模式继续作为可选导出能力

### 结果 2

发现了额外字段，但只是现有图片/视频地址的等价表达。

结论：

- 不值得改造主链路
- 只在文档中记录字段认知

### 结果 3

发现了明显更原始、更完整的实况资源字段或关联接口。

结论：

- 再单独立项评估接入成本与收益
- 不在本计划中直接修改当前下载系统

## 停止条件

为了控制投入，本计划应设置明确停止条件。满足以下任一条件即可停止：

1. 已验证多个入口返回的核心结构一致，均为 `image + video`
2. 未发现任何稳定可复现的更原始字段
3. 新发现字段无法稳定获取，或高度依赖易失效的端内环境
4. 继续研究的投入明显高于潜在收益

## 风险与成本

如果未来决定启动该计划，需要预先接受这些风险：

- 不同端接口可能频繁变动
- 字段命名可能混淆且缺乏公开语义
- 某些字段可能依赖登录态、设备信息或特定版本 App
- 最终很可能得出“当前实现已经足够好”的结论

因此该计划应始终保持“小投入、快验证、早收敛”的原则。

## 当前建议

在没有新证据前，项目应维持以下策略：

- 将抖音 `实况` 视为 `图片 + 动态视频` 的平台内容模型
- 默认导出为 `jpeg + mp4`
- 在需要更接近 Apple 风格时，允许切换为 `jpeg + mov`
- 不把“寻找上游封装好的 live 文件”作为当前开发主线

## 后续触发条件

仅当满足以下情况之一时，再启动本计划：

- 用户明确提出继续追查上游原始实况资源
- 抓包中出现新的可疑字段或资源地址
- 新版本抖音接口表现出与当前结构显著不同的返回
- 当前 `jpeg + mp4` 导出方案无法满足新的明确业务需求

## 当前验证进展（2026-03-22）

本轮已基于 3 个真实用户样本做了第一轮 Web 侧字段验证。

### 样本结果

1. 样本一
   - 短链落地页：`/note/7617127364405264613`
   - 页面标题：`有我就够了吗。#素颜原相机`
   - 结论：有效实况样本

2. 样本二
   - 短链落地页：`/note/7607761366414206314`
   - 页面标题：`我就当我的爱 是罪 是东流水 #舞蹈生 #健身ootd #增肌小姐姐`
   - 结论：有效实况样本

3. 样本三
   - 短链落地页：`/video/7301946532788555046`
   - 页面标题：`听说上热门了，我就把原图无修的实况图分享出来～希望能带你感受当时的风和夕阳🌅`
   - 结论：当前公开首屏详情不呈现 `note` 型实况结构，暂不作为本轮主证据样本

### 对样本一与样本二的共同验证结论

通过解析公开 Web 页面首屏注入数据，可以确认：

1. 两个有效样本的详情数据都包含 `detail.images`
2. `detail.images[*]` 均包含以下关键字段：
   - `urlList`
   - `downloadUrlList`
   - `video`
   - `clipType`
   - `livePhotoType`
3. 两个有效样本中，`detail.images[0].livePhotoType` 均为 `1`
4. `detail.images[*].video` 内部仍然是常规视频表达，包括：
   - `playAddr`
   - `playApi`
   - `bitRateList`
   - `playAddrFileHash`
   - `meta`
5. 当前没有发现单独的“live 单文件”字段

### 当前新增认知

本轮新增且稳定出现的字段线索是：

- `livePhotoType`

这说明公开详情中确实存在“实况标记”字段，而不是只能通过“图片项里是否有 `video`”来间接判断。

当前可以先将其视为：

- `detail.images[*].video`：动态部分资源
- `detail.images[*].livePhotoType`：实况语义标记

### 当前仍未发现的字段

在样本一与样本二的公开首屏详情中，尚未发现以下字段：

- `live_photo`
- `motion_photo`
- `paired_video`
- `asset_id`
- `content_id`

同时也没有看到明显可直接指向 Apple 配对资产的公开元数据。

### 阶段性结论

基于当前两条有效样本，已经可以得出一个更强的阶段性判断：

- 公开 Web 详情接口对抖音实况的表达，至少稳定包含 `images[*].video`
- 公开 Web 详情接口同时存在 `livePhotoType` 这一实况标记字段
- 当前仍没有证据表明公开接口暴露了比 `image + video` 更原始的单体 live 资源

因此，本计划当前更接近“结果 2 与结果 1 之间”：

- 已发现额外字段，但它更像是现有语义的补充标记
- 尚未发现足以触发主链路改造的更原始资源表达

### 多入口对比补充结论

本轮还对以下两个入口做了直接比对：

- Web 页面首屏注入详情数据
- 当前项目所使用的 `aweme/v1/web/aweme/detail` 接口

对样本一与样本二的比较结果一致：

1. 两个入口的核心实况语义一致
2. 差异主要体现在字段命名风格，而不是资源结构

可对应的字段示例如下：

- Web 首屏注入：
  - `livePhotoType`
  - `clipType`
  - `urlList`
  - `downloadUrlList`
  - `playAddr`
  - `bitRateList`

- `aweme/detail` 接口：
  - `live_photo_type`
  - `clip_type`
  - `url_list`
  - `download_url_list`
  - `play_addr`
  - `bit_rate`

在两个有效样本中，下列关键值均保持一致：

- `awemeType`
- `mediaType`
- `images` 数量
- 首个图片项的 `livePhotoType / live_photo_type`
- 首个图片项的 `clipType / clip_type`
- `images[*]` 中是否包含 `video`

当前观察到的一个小差异是：

- Web 首屏注入数据中的 `video` 对象可见 `playApi`
- `aweme/detail` 接口返回中未直接看到等价的 `play_api`

但该差异不足以改变主结论，因为两者在“实况由 `images[*].video` 表达”的核心结构上仍然一致。

据此可以进一步判断：

- 当前项目所使用的 `aweme/detail` 链路，已经拿到了与 Web 首屏一致的实况核心数据
- 目前没有证据表明 Web 首屏比 `aweme/detail` 多暴露出一个更原始的公开 live 资源入口

### `images[*].video` 子对象排查补充结论

本轮进一步收窄到 `detail.images[*].video` 本身，重点检查是否存在“上传端原始素材”或“未转码资源”痕迹。

当前看到的字段更接近“分发后的视频播放资源描述”，而不是“上传源文件描述”。

在有效样本中，`images[*].video` 及其码率项里稳定出现的字段主要包括：

- `play_addr / playAddr`
- `download_addr`
- `bit_rate / bitRateList`
- `playApi`
- `file_hash`
- `fileId`
- `videoFormat / format`
- `gearName`
- `qualityType`
- `fps`

这些字段说明：

1. 当前拿到的是已经可播放、可分发的动态视频资源
2. 资源具备典型的转码/分发属性，例如：
   - 码率档位
   - 分辨率
   - `format = mp4`
   - `gearName = normal_720_0`
   - 播放地址与 `play` 接口
3. 能看到 `fileId`、`file_hash` 一类分发资源标识，但它们更像 CDN / 播放链路使用的文件标识，而不是上传端原始实况资产标识

当前没有看到的内容包括：

- 明确标记“原始上传文件”的字段
- 未转码容器格式说明
- Apple 配对元数据
- 单独的原始动态照片资产 ID
- 明确区分“源素材”和“分发素材”的公开字段

因此目前更合理的判断是：

- `images[*].video` 指向的是平台已处理后的动态视频资源
- 它可以视为实况动态部分的公开分发结果
- 但还不能据此证明公开接口暴露了上传端原始 live 素材

### `download_addr` 与 `play_addr` 的补充判断

本轮还进一步关注了 `video.download_addr` 与 `video.play_addr` 的差异，尝试判断：

- `download_addr` 是否比 `play_addr` 更接近原始素材
- `download_addr` 是否暴露了更高层级的 live 资产表达

当前阶段的判断是：

- 尚未看到 `download_addr` 比 `play_addr` 更“原始”的明确证据
- 两者都更像平台分发链路下的资源地址，而不是上传端原始 live 素材入口

作出这一判断的依据是：

1. `video` 整体仍然伴随明显的分发/转码字段，例如：
   - `bit_rate`
   - `format = mp4`
   - `gear_name`
   - `quality_type`
   - `fps`
   - `fileId`
   - `file_hash`
2. 即使存在 `download_addr`，当前也没有看到它带出以下更高层级信息：
   - 原始上传容器
   - 原始 live 资产 ID
   - Apple 配对元数据
   - 明确区分“源素材”和“分发素材”的公开标记

需要保留的限制说明是：

- 在浏览器环境中，`aweme/detail` 对部分样本存在间歇性空响应
- 因此本轮没有稳定拿到足够多组完整的 `download_addr` 与 `play_addr` 对照样本

所以目前最稳妥的表述应当是：

- `download_addr` 未显示出更原始素材的明显迹象
- 但这仍属于阶段性结论，而不是对两者完全等价的严格证明

结合前述所有验证结果，本计划在公开入口层面已经基本可以收束为：

- 实况的公开表达稳定为 `images[*] + video + live_photo_type`
- `video` 更像动态部分的公开分发资源
- 目前没有发现公开接口暴露上传端原始 live 素材
